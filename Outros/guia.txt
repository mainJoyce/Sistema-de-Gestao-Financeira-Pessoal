Documentação Técnica — Sistema de Gestão Financeira Pessoal

Esta documentação deve funcionar como o documento-base do projeto, servindo para vocês definirem arquitetura, banco de dados, backend, regras de negócio, APIs, desenvolvimento e testes.

## 1. Identificação do Projeto

Nome: Sistema de Gestão Financeira Pessoal
Tipo:** Aplicação web de gestão financeira
*Objetivo:** Controle, análise e planejamento das finanças pessoais
**Backend:** Java + Spring
**Arquitetura:** API REST em camadas
**Banco de dados:** a definir
**Frontend:** a definir
**Versionamento do código:** Git + GitHub

---

# 2. Objetivo do Sistema

Desenvolver uma plataforma capaz de centralizar as informações financeiras do usuário e transformá-las em informações úteis para tomada de decisão.

O sistema deverá permitir:

* cadastrar receitas;
* cadastrar despesas;
* categorizar transações;
* acompanhar saldo;
* criar orçamentos;
* acompanhar consumo dos orçamentos;
* gerar indicadores;
* visualizar gráficos;
* gerar relatórios;
* criar metas financeiras;
* acompanhar patrimônio;
* analisar comportamento financeiro;
* emitir alertas;
* gerar insights;
* calcular score de saúde financeira;
* fornecer recomendações financeiras baseadas nas regras definidas.

---

# 3. Escopo do MVP
Como o projeto possui muitas funcionalidades, **não é recomendável desenvolver tudo simultaneamente.

O MVP deve priorizar o núcleo financeiro.

### MVP — Obrigatório

1. Cadastro/login de usuário
2. Cadastro de receitas
3. Cadastro de despesas
4. Consulta de transações
5. Edição de transações
6. Exclusão controlada de transações
7. Categorias
8. Dashboard
9. Cálculo de receita
10. Cálculo de despesas
11. Cálculo de saldo
12. Orçamentos
13. Percentual utilizado do orçamento
14. Alertas de orçamento
15. Relatórios básicos

### Segunda etapa

* metas financeiras;
* mapeamento salarial;
* regra 50/30/20;
* comparação mensal;
* gastos recorrentes;
* patrimônio;
* score financeiro.

### Terceira etapa

* insights automáticos;
* categorização automática;
* recomendações;
* importação bancária;
* análise mais avançada de comportamento.

> **Importante:** a integração bancária e funcionalidades de inteligência devem ser tratadas como etapas posteriores. Elas aumentam bastante a complexidade do projeto.

# 4. Arquitetura

A arquitetura recomendada para o backend é:

```text
Frontend
    │
    │ HTTP/JSON
    ▼
┌───────────────────────────┐
│       REST API            │
├───────────────────────────┤
│ Controllers               │
├───────────────────────────┤
│ Services                  │
├───────────────────────────┤
│ Repositories              │
├───────────────────────────┤
│ JPA / Hibernate           │
└─────────────┬─────────────┘
              │
              ▼
        Banco de Dados
```

### Responsabilidade de cada camada

**Controller**

Recebe requisições HTTP e devolve respostas.

**Service**

Contém as regras de negócio.

**Repository**

Responsável pelo acesso aos dados.

**Entity**

Representa as entidades persistidas no banco.

**DTO**

Define os dados que entram e saem da API.

```text
--------------------
```

### Regras

* `id` deve ser único.
* `email` deve ser único.
* senha nunca deve ser armazenada em texto puro.
* salário não pode ser negativo.
* usuário deve possuir suas próprias transações.

# 26. Regras de negócio

As regras devem ficar documentadas e implementadas na camada `Service`.

## RN001

Toda transação pertence a um usuário.

## RN002

Uma despesa possui uma categoria principal.

## RN003

Valor deve ser maior que zero.

## RN004

Orçamentos são mensais por padrão.

## RN005

Histórico financeiro deve ser preservado.

## RN006

Insights somente quando houver dados suficientes.

## RN007

Recomendações consideram renda atual.

## RN008

Score é recalculado quando houver alterações relevantes.

## RN009

Relatórios mensais devem possuir histórico.

---

# 27. Regras do orçamento

Implementar uma função conceitual:

```text
percentual = (valorGasto / limite) × 100
```

Depois:

```text
0–70     → NORMAL
71–89    → ATENCAO
90–100   → RISCO
>100     → ESTOURADO
```

### Exemplo

Limite:

R$ 1.000

Gasto:

R$ 750

Percentual:

75%

Status:

**ATENÇÃO**

---

# 28. Regras do saldo

```text
saldo = receitas - despesas
```

Exemplo:

```text
Receitas = 5000
Despesas = 3200

Saldo = 1800
```

---

# 29. Comprometimento da renda

```text
(desposas / receitas) × 100
```

Exemplo:

```text
3200 / 5000 × 100
= 64%
```

---

# 30. Regra 50/30/20

A implementação deve utilizar a renda líquida:

```text
necessidades = renda × 0.50
desejos = renda × 0.30
investimentos = renda × 0.20
```

Exemplo:

```text
Renda = 5000

Necessidades = 2500
Desejos = 1500
Investimentos = 1000
```

---

# 31. Reserva de emergência

Uma implementação inicial pode utilizar:

```text
reservaIdeal = despesasMedias × mesesReserva
```

Exemplo:

```text
despesas médias = 3000
meses = 6

reserva ideal = 18000
```

O número de meses deve ser tratado como **parâmetro de negócio**, e não necessariamente ficar fixo no código.

---

# 32. Metas financeiras

Fórmulas:

### Valor restante

```text
valorObjetivo - valorAcumulado
```

### Percentual

```text
(valorAcumulado / valorObjetivo) × 100
```

### Valor mensal necessário

```text
valorRestante / mesesRestantes
```

---

# 33. Insights

Os insights devem ser implementados inicialmente com regras simples.

Exemplo:

```text
Se gastoAtual > gastoAnterior × 1.30
→ gerar alerta de aumento significativo
```

Outro:

```text
Se orçamento >= 90%
→ gerar alerta de risco
```

Outro:

```text
Se orçamento > 100%
→ gerar alerta de orçamento excedido
```

Isso permite criar a inteligência do sistema sem precisar começar com IA.

# 34. Categorização automática

Criar inicialmente uma tabela ou estrutura de regras:

```text
Estabelecimento → Categoria
```

Exemplo:

```text

McDonald's → ALIMENTACAO
```

A lógica deve ser substituível no futuro.

Assim, futuramente vocês podem trocar:

por:

sem precisar reescrever todo o sistema.

# 35. Tratamento de erros

A API precisa utilizar respostas HTTP apropriadas.

### 200

Requisição processada com sucesso.

### 201

Recurso criado.

### 204

Operação realizada sem conteúdo de retorno.

### 400

Dados inválidos.

### 401

Usuário não autenticado.

### 403

Usuário autenticado, mas sem permissão.

### 404

Recurso não encontrado.

### 409

Conflito.

### 500

Erro interno.

Utilizar Bean Validation.

Exemplos conceituais:

```text
@NotBlank
```

para descrição.

```text
@NotNull
```

para campos obrigatórios.

```text
@Positive
```

para valores financeiros.

```text

```

para e-mail.

A validação deve existir **antes da aplicação das regras de negócio**.

# 37. Segurança

Como o sistema trabalha com dados financeiros, segurança é um requisito crítico.

Implementar:

* autenticação;
* autorização;
* senha com hash;
* JWT;
* validação de entrada;
* proteção de endpoints;
* separação de dados por usuário;
* controle de acesso.

Um usuário não pode fazer:

```http
GET /api/transacoes/123
```

e receber uma transação pertencente a outro usuário.

---

# 42. Transações de banco

Operações que alteram várias informações devem ser tratadas cuidadosamente.

Por exemplo:

```text
Cadastrar transação
      ↓
Salvar transação
      ↓
Atualizar orçamento
      ↓
Atualizar indicadores
```

Se uma operação crítica falhar no meio, o banco não deve ficar em estado inconsistente.

No Spring, isso normalmente é tratado através de transações com `@Transactional`.

# 52. Regra mais importante para a equipe

Antes de implementar qualquer funcionalidade, vocês devem conseguir responder:

> **Qual é a regra de negócio dessa funcionalidade?**

Por exemplo:

**"Criar orçamento"**

não deve ser simplesmente:

> Fazer um POST.

Vocês precisam definir:

* quem pode criar;
* qual categoria pode receber;
* se pode existir mais de um orçamento da mesma categoria no mesmo mês;
* qual valor mínimo;
* como o consumo será calculado;
* quando o alerta será disparado;
* o que acontece quando o orçamento é alterado;
* como o histórico será preservado.

Essa abordagem evita que cada integrante implemente uma interpretação diferente do sistema.

# 53. Fluxo geral que vocês devem ter em mente

O projeto inteiro pode ser resumido desta forma:

```text
                              │
                              ▼
```

Essa deve ser a **visão arquitetural de alto nível** que orienta o desenvolvimento.

O ponto central é: **primeiro construam uma base financeira confiável — usuários, transações, categorias, orçamento e histórico. Depois construam a inteligência em cima desses dados.** Isso torna o projeto muito mais fácil de dividir entre vocês, testar e evoluir sem criar dependências desnecessárias.
